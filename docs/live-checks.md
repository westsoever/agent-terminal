# Live checks: what they prove and who runs them

Everything under `tests/t_*.sh` runs in a sandbox and never touches the real machine. These do touch it, so they are separate and optional.

| Check | What it does | Safe to run | Needs |
|---|---|---|---|
| `tests/live-smoke.sh` | Sections 0 to 2 (there is no section 3): the hooks generated by `install.sh` against a real `claude -p` (haiku, about US$0.10), everything in `/tmp`. Section 4: speaks one sentence through Kokoro and reads the keyboard idle time with `ioreg`. Section 5: runs `live-watch.sh` read-only on the real launchd job. | Daytime only (section 4 makes sound) | Kokoro on port 8880, `claude` logged in |
| `tests/live-watch.sh` | Silent and read-only: the launchd job `org.ching.watch` is loaded, its run counter and last exit code, the script it runs exists and parses, `watch.log`, and the newest event only the watcher writes. `--kick` starts one extra run (`launchctl kickstart` without `-k`, so a run in progress is never killed) and waits for launchd's `runs` counter to go up. | Any time | nothing |
| `bin/sync-check.sh` | The read-only git sync check on every repo Ching knows (see `ching-functions.md` section 6). Runs `git fetch`; changes nothing else. | Any time; it prints a one-line summary and writes `~/.agent/sync-check.md` | network for the fetch |
| `bin/metrics.sh` | Pilot metrics per day from `events.jsonl`. | Any time, read-only | nothing |

## What `live-watch.sh` reading means

- `watch.log` is empty on a healthy machine: the watcher prints nothing when it works. Errors, and anything the background sync check reports, land there.
- A missing or old watcher event is a warning, not a failure: an idle machine has no live session and so no watcher event.
- `runs` is launchd's own counter. It goes up on every tick (every 300 s) and on a kickstart.

## What cannot be checked without the owner

- **The spoken note from launchd** (PLAN 1.6.5, the part with ears): that the real job reaches Kokoro, `ioreg` and the audio output under launchd's own PATH, outside quiet hours. Daytime only: run `tests/live-smoke.sh` (section 4) and then the step 5 sequence in `docs/superpowers/plans/2026-10-05-ching-nudge.md` with a fake waiting session, and listen.
- **Which client a session came from** (Desktop, VS Code or CLI): `events.jsonl` does not record the entrypoint.
- **A real release through the release gate** with the owner watching (PLAN 2.6): no release has gone through it yet (`bin/metrics.sh` shows one gate failure and no pass).
